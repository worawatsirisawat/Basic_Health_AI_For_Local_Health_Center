# Local Health AI

ระบบผู้ช่วย AI สำหรับเจ้าหน้าที่สาธารณสุขและ อสม. ที่ปฏิบัติงานใน รพ.สต. พื้นที่ห่างไกล ทำหน้าที่ช่วยซักประวัติ ประเมินบาดแผลจากภาพถ่าย และเสนอทางเลือกการดูแลจากยาและเวชภัณฑ์ที่หน่วยบริการมีอยู่จริงในวันนั้น โดยเจ้าหน้าที่เป็นผู้ตัดสินใจสุดท้ายเสมอ

คำถามที่ระบบนี้ตอบไม่ใช่ว่าผู้ป่วยรายนี้ควรได้ยาอะไรตามตำรา แต่เป็นว่าด้วยยาที่หน่วยบริการนี้มีอยู่จริงวันนี้ จะดูแลผู้ป่วยรายนี้ได้ดีที่สุดอย่างไร

---

## เริ่มใช้งาน

บน Windows ดับเบิลคลิก `run.bat` บน macOS หรือ Linux รัน `./run.sh` แล้วเปิดเบราว์เซอร์ไปที่ http://127.0.0.1:8000

เข้าสู่ระบบด้วยชื่อผู้ใช้ `local_health_care_user` หรือ `admin_xyz_health_care` รหัสผ่าน `1234` แล้วเลือกหน่วยบริการ ระบบทำงานได้ทันทีโดยไม่ต้องมี API key เพราะมี Mock mode ในตัว เมื่อต้องการใช้ Typhoon จริงให้คัดลอก `.env.example` เป็น `.env` แล้วใส่ค่า `TYPHOON_API_KEY`

บัญชีผู้ใช้ชุดนี้เป็น placeholder สำหรับทดสอบเท่านั้น ต้องเปลี่ยนเป็นรหัสหน่วยบริการที่ออกโดยหน่วยงานต้นสังกัดพร้อมการเก็บรหัสผ่านแบบ hash ก่อนนำไปใช้จริง

ความต้องการของระบบอยู่ใน `requirements.txt` ได้แก่ FastAPI, uvicorn, Pillow, NumPy, requests, python-multipart และ pydantic ส่วนการค้นคืนคู่มือออฟไลน์ใช้เฉพาะไลบรารีมาตรฐานของ Python ไม่ต้องติดตั้งเพิ่ม

## ภาพรวมสถาปัตยกรรม

ระบบแบ่งเป็นห้าชั้นที่ทำงานเรียงกันจากล่างขึ้นบน ชั้นล่างมีอำนาจเหนือชั้นบนเสมอ

| ชั้น | หน้าที่ | ไฟล์ที่รับผิดชอบ | AI ยกเลิกได้หรือไม่ |
|---|---|---|---|
| 1. กฎความปลอดภัยตายตัว | ตรวจจับอาการและลักษณะแผลที่ต้องส่งต่อทันที | `triage_service.py` กับ `data/red_flags.json` | ไม่ได้ เด็ดขาด |
| 2. การวิเคราะห์เชิงตัวเลข | คำนวณสัดส่วนเนื้อเยื่อ ขนาด และคะแนนความเสี่ยงติดเชื้อจากภาพ | `wound_service.py` | ไม่ได้ เป็นค่าที่คำนวณตายตัว |
| 3. ข้อมูลทรัพยากรจริง | บัญชียาและเวชภัณฑ์คงเหลือของหน่วยบริการนั้น | `medicine_service.py` | ไม่ได้ AI แนะนำได้เฉพาะสิ่งที่มีในบัญชี |
| 4. หลักฐานอ้างอิง | คู่มือในเครื่องแบบออฟไลน์ และงานวิจัยจาก PubMed | `knowledge_service.py` กับ `pubmed_service.py` | ไม่ได้ เป็นข้อความที่ค้นมาจริง |
| 5. การประเมินยืดหยุ่น | ซักประวัติต่อเนื่อง เรียบเรียงคำแนะนำและขั้นตอนการทำแผล | `llm_service.py` | ชั้นนี้เองคือส่วนที่ยืดหยุ่น |

เหตุผลที่ต้องวางชั้นที่ 1 ไว้ล่างสุดเพราะงานวิจัยพบว่า AI symptom checker ให้คำวินิจฉัยถูกต้องเป็นอันดับแรกเพียงราวสามสิบกว่าเปอร์เซ็นต์ การปล่อยให้โมเดลประเมินความเสี่ยงเองล้วนจะทำให้จุดที่อันตรายที่สุดไม่มีตาข่ายนิรภัยรองรับ

## หลักการทำงานของชั้นความปลอดภัย

`data/red_flags.json` เก็บกฎไว้ 15 ข้อ แบ่งเป็นกฎด้านอาการ 10 ข้อและกฎด้านบาดแผล 5 ข้อ บุคลากรทางการแพทย์แก้ไขไฟล์นี้ได้โดยตรงโดยไม่ต้องแตะโค้ด แล้วเรียก `/api/system/rules/reload` เพื่อให้ระบบโหลดกฎใหม่ทันทีโดยไม่ต้องรีสตาร์ต

กฎด้านอาการใช้การจับคู่คำแบบมีเงื่อนไขร่วม เพื่อลดการเตือนผิดพลาด คำว่าเจ็บหน้าอกเพียงลำพังไม่ทำให้กฎทำงาน ต้องมีอาการร่วมอย่างหายใจลำบากหรือเหงื่อแตกด้วยจึงจะเข้าเกณฑ์ เหตุผลคือถ้าระบบเตือนผิดบ่อยเกินไป เจ้าหน้าที่จะเลิกเชื่อการแจ้งเตือนทั้งหมด ซึ่งอันตรายกว่าการไม่มีระบบเตือนเลย

กฎด้านบาดแผลมีบทเรียนสำคัญฝังอยู่หนึ่งข้อ กฎเรื่องขนาดแผลเกิน 5 เซนติเมตรจะทำงานก็ต่อเมื่อเจ้าหน้าที่ระบุขนาดอ้างอิงของภาพไว้แล้วเท่านั้น ถ้ายังไม่ได้สอบเทียบ ระบบจะไม่บังคับส่งต่อ แต่แจ้งเป็นข้อสังเกตให้ไปวัดจริงด้วยไม้บรรทัดแทน เพราะการประมาณขนาดจากสมมติฐานระยะถ่ายภาพเชื่อถือไม่ได้พอที่จะใช้ตัดสินใจ

เมื่อกฎทำงาน ระบบจะหยุดกระบวนการทั้งหมดทันทีและตอบกลับด้วย `phase: "refer_immediately"` พร้อมระบุว่าการแจ้งเตือนนี้มาจากกฎตายตัว ไม่ได้มาจากการประเมินของ AI เพื่อให้เจ้าหน้าที่แยกออกว่าข้อความใดเชื่อถือได้ระดับใด

## Medicine Mode หลักการทำงาน

โหมดปรึกษาอาการทำงานเป็นลำดับดังนี้

1. เจ้าหน้าที่พิมพ์อาการที่ผู้ป่วยบอก ระบบรวมข้อความของผู้ใช้ทุกรอบเข้าด้วยกันเป็นข้อความเดียวสำหรับตรวจกฎ
2. `triage_service.check_symptoms()` ตรวจข้อความนั้นกับกฎ 10 ข้อ ถ้าเข้าเกณฑ์จะหยุดทันทีโดยไม่เรียกโมเดลเลย
3. ถ้าไม่เข้าเกณฑ์ ระบบดึงบัญชียาที่มีคงเหลือมากกว่าศูนย์ของหน่วยบริการนั้น แปลงเป็นข้อความด้วย `format_for_prompt()` แล้วส่งเข้า prompt
4. ถ้าเปิดใช้ PubMed ระบบค้นงานวิจัยที่เกี่ยวข้องแล้วแนบเป็นหลักฐานประกอบ
5. โมเดลซักถามกลับทีละคำถามโดยปรับคำถามตามคำตอบก่อนหน้า อย่างน้อย 3 คำถามและไม่เกิน 5 คำถาม ตามค่า `MIN_QUESTIONS` และ `MAX_QUESTIONS`
6. เมื่อข้อมูลพอ ระบบสรุปคำแนะนำพร้อมเหตุผลว่าอ้างอิงจากอาการใด และแยกแหล่งที่มาให้ชัดว่าส่วนใดมาจากบัญชียา ส่วนใดมาจากงานวิจัย

## Wounded Mode หลักการทำงาน

โหมดประเมินบาดแผลทำงานเป็นลำดับดังนี้

1. เจ้าหน้าที่อัปโหลดภาพแล้วลากกรอบสี่เหลี่ยมครอบบริเวณแผล ซึ่งเป็นการโต้ตอบที่ง่ายพอสำหรับผู้ที่ไม่คุ้นเคยกับเทคโนโลยี
2. `strip_metadata_and_save()` สร้างภาพขึ้นใหม่จากข้อมูลพิกเซลดิบ ทำให้ EXIF และพิกัด GPS หายไปทั้งหมดก่อนบันทึกลงดิสก์
3. `quick_quality_check()` ประเมินความสว่างและความแปรปรวนเพื่อเตือนภาพเบลอหรือมืดเกินไป โดยไม่บล็อกการทำงาน
4. `segment_from_bbox()` ตัดเฉพาะบริเวณในกรอบตามสัดส่วนของภาพ
5. `_classify_pixel()` จำแนกทุกพิกเซลในบริเวณนั้นตามค่าสีในปริภูมิ HSV เป็นชนิดเนื้อเยื่อ แล้ว `analyze_region()` รวมเป็นสัดส่วน ขนาดโดยประมาณ และคะแนนความเสี่ยงติดเชื้อ
6. `triage_service.check_wound()` ตรวจผลตัวเลขนั้นกับกฎด้านบาดแผล 5 ข้อ
7. ระบบดึงเวชภัณฑ์ทำแผลที่มีจริง ค้นหลักฐานจาก PubMed แล้วส่งทั้งหมดให้โมเดลเรียบเรียงขั้นตอนการทำแผล
8. ถ้าเข้าเกณฑ์อันตราย หน้าจอจะแสดงกล่องแจ้งเตือนที่ให้เลือกสองทาง คือส่งต่อโรงพยาบาลทันที หรือขอถามต่อกับระบบ

เกณฑ์การจำแนกพิกเซลใช้กฎแบบลำดับก่อนหลัง ค่าความสว่างต่ำกว่า 0.22 ถือเป็นเนื้อคล้ำ ค่าความอิ่มตัวต่ำถือเป็นพื้นหลังอย่างผ้าก๊อซหรือแสงสะท้อน โทนแดงที่อิ่มตัวสูงถือเป็นเนื้อแดงที่กำลังสมานตัว โทนเหลืองถึงเขียวถือเป็นเนื้อเหลืองที่อาจเป็นหนอง

## หลักการเชื่อมโยงข้อมูลยากับแผลและคำปรึกษา

ส่วนนี้เป็นหัวใจของระบบ เพราะเป็นสิ่งที่ทำให้คำแนะนำใช้ได้จริงในหน่วยบริการที่ยาขาดบ่อย

### ข้อมูลยาเข้าสู่การตัดสินใจอย่างไร

บัญชียาผูกกับรหัสหน่วยบริการเสมอ ตาราง `medicines` มีคีย์ไม่ซ้ำเป็นคู่ของรหัสหน่วยบริการกับชื่อยา ดังนั้นหน่วยบริการแต่ละแห่งมีบัญชีของตัวเองแยกกันสมบูรณ์ เมื่อเจ้าหน้าที่เข้าสู่ระบบและเลือกหน่วยบริการ ทุกคำแนะนำหลังจากนั้นจะอ้างอิงบัญชีของหน่วยนั้นเท่านั้น

ทั้งสองโหมดดึงบัญชียาด้วยวิธีที่ต่างกันตามบริบทการใช้งาน

| โหมด | วิธีดึงรายการ | เหตุผล |
|---|---|---|
| Medicine Mode | ดึงยาทุกรายการที่คงเหลือมากกว่าศูนย์ | อาการที่ปรึกษามีได้หลากหลาย จึงต้องให้โมเดลเห็นตัวเลือกทั้งหมด |
| Wounded Mode | ดึงเฉพาะหมวดเวชภัณฑ์ทำแผล ถ้าไม่มีเลยจึงถอยไปดึงทั้งบัญชี | การทำแผลใช้เวชภัณฑ์เฉพาะกลุ่ม การส่งรายการยากินทั้งหมดเข้าไปทำให้โมเดลเสนอสิ่งที่ไม่เกี่ยวข้อง |

รายการที่ได้จะถูกแปลงด้วย `format_for_prompt()` เป็นข้อความที่ระบุชื่อ หมวด จำนวนคงเหลือ และข้อบ่งใช้ของแต่ละรายการ จำกัดไม่เกิน 40 รายการเพื่อไม่ให้กิน context เกินจำเป็น ข้อความนี้ถูกใส่เข้า prompt พร้อมกติกาที่ระบุชัดว่าห้ามแนะนำสิ่งที่ไม่อยู่ในรายการนี้

### การหายาทดแทนเมื่อยาที่เหมาะที่สุดไม่มี

`SUBSTITUTE_GROUPS` เป็นตารางที่แมปหมวดยาหนึ่งไปยังหมวดที่ทดแทนกันได้ในเชิงข้อบ่งใช้เบื้องต้น ตรรกะนี้ทำงานในโค้ดจริงเสมอ ไม่ใช่ส่วนที่จำลอง และไม่ขึ้นกับว่าใช้ Mock mode หรือ Typhoon จริง

| หมวดที่ต้องการ | หมวดที่ระบบยอมให้ทดแทนได้ |
|---|---|
| ยาแก้ปวดลดไข้ | ยาแก้ปวดลดไข้ และยาแก้อักเสบไม่ใช่สเตียรอยด์ |
| ยาแก้อักเสบไม่ใช่สเตียรอยด์ | ยาแก้อักเสบไม่ใช่สเตียรอยด์ และยาแก้ปวดลดไข้ |
| ยาทาปฏิชีวนะ | ยาทาปฏิชีวนะ และเวชภัณฑ์ทำแผล |
| ยาทาแผลไฟไหม้ | ยาทาแผลไฟไหม้ และเวชภัณฑ์ทำแผล |
| ยาปฏิชีวนะ | ยาปฏิชีวนะ เท่านั้น ไม่ยอมให้ข้ามกลุ่ม |
| ยาแก้แพ้ ยาลดกรด ยาแก้คลื่นไส้ ยาแก้ไอ สารน้ำทดแทน เวชภัณฑ์ทำแผล | หมวดตัวเองเท่านั้น |

หลักที่ใช้ตัดสินว่าหมวดใดทดแทนกันได้คือความเสี่ยงถ้าเลือกผิด หมวดที่มีข้อบ่งใช้ทับซ้อนกันมากและความเสี่ยงต่ำอย่างยาแก้ปวดลดไข้กับยาแก้อักเสบไม่ใช่สเตียรอยด์จึงทดแทนกันได้ ส่วนยาปฏิชีวนะไม่ยอมให้ทดแทนข้ามกลุ่มเลย เพราะการเลือกยาปฏิชีวนะผิดกลุ่มมีผลต่อทั้งตัวผู้ป่วยและปัญหาเชื้อดื้อยาในระดับชุมชน เรื่องนี้เกินขอบเขตที่ระบบช่วยตัดสินใจแทนได้

ตารางนี้ยังไม่ผ่านการตรวจสอบโดยเภสัชกร ใช้สาธิตระบบเท่านั้น

### เหตุใดระบบจึงไม่หักสต็อกอัตโนมัติ

เมื่อ AI แนะนำยา ระบบไม่หักจำนวนคงเหลือให้เอง เจ้าหน้าที่ต้องปรับจำนวนเองเป็นรอบ เหตุผลคือคำแนะนำของระบบไม่เท่ากับการจ่ายยาจริง เจ้าหน้าที่อาจไม่ทำตามคำแนะนำ อาจจ่ายจำนวนต่างจากที่แนะนำ หรืออาจไม่ได้จ่ายเลย ถ้าหักอัตโนมัติ ตัวเลขในระบบจะเพี้ยนจากของจริงอย่างรวดเร็ว แล้วคำแนะนำรอบถัดไปจะอ้างอิงบัญชีที่ผิด ซึ่งอันตรายกว่าการให้เจ้าหน้าที่อัปเดตเอง

ยาที่เจ้าหน้าที่เพิ่มเองจะถูกบันทึก `is_custom = 1` ไว้ เพื่อให้ตรวจสอบย้อนหลังได้ว่ารายการใดมาจากการกรอกเองและไม่ได้ผ่านการตรวจสอบกับฐานข้อมูลกลาง ระบบมี autocomplete จากรายการยาที่พบบ่อยเพื่อลดการพิมพ์ชื่อยาผิด ซึ่งทำงานแบบ local ล้วน ไม่เรียก API ภายนอก

### การเชื่อมผลวิเคราะห์ภาพเข้ากับเวชภัณฑ์

ในโหมดบาดแผล ผลตัวเลขจากการวิเคราะห์ภาพถูกส่งเข้า prompt พร้อมรายการเวชภัณฑ์ที่มีจริง โมเดลจึงเรียบเรียงขั้นตอนการทำแผลโดยอ้างอิงของที่หยิบใช้ได้จริงในห้องนั้น ไม่ใช่ขั้นตอนตามตำราที่ต้องใช้ของที่หน่วยบริการไม่มี

เมื่อข้อความบรรยายของเจ้าหน้าที่ขัดแย้งกับผลจากภาพ ระบบยึดคำบรรยายของเจ้าหน้าที่เป็นหลักเสมอ แล้วบันทึกความขัดแย้งนั้นไว้ในช่อง `conflict_note` เหตุผลคือเจ้าหน้าที่เห็นแผลจริงต่อหน้า ส่วนภาพถ่ายอาจเพี้ยนจากแสง เงา สีผิว และมุมกล้อง

## ชั้นโมเดลภาษา Typhoon และ Mock mode

ระบบสลับโหมดอัตโนมัติจากการมีหรือไม่มี `TYPHOON_API_KEY` ทั้งสองเส้นทางคืนโครงสร้างข้อมูลหน้าตาเหมือนกันทุกประการ ส่วนอื่นของระบบจึงไม่ต้องรู้ว่ากำลังใช้เส้นทางไหน

Mock mode ไม่ใช่ข้อความสำเร็จรูปที่เขียนตายตัว แต่เป็นระบบกฎที่ตัดสินใจจริง ใช้ชุดคำถาม 5 ข้อและกฎแมปอาการไปยังหมวดยา 7 ข้อ ทำงานแบบพบข้อแรกที่ตรงแล้วหยุด

| คำสำคัญที่ตรวจจับ | หมวดยาที่เสนอ |
|---|---|
| ไข้ ตัวร้อน ปวดหัว ปวดศีรษะ | ยาแก้ปวดลดไข้ |
| ไอ เสมหะ เจ็บคอ คอแห้ง | ยาแก้ไอ |
| ท้องเสีย ถ่ายเหลว ถ่ายบ่อย ท้องร่วง | สารน้ำทดแทน |
| คัน ผื่น ลมพิษ แพ้ | ยาแก้แพ้ |
| แสบท้อง จุกเสียด แน่นท้อง กรดไหลย้อน | ยาลดกรด |
| คลื่นไส้ อาเจียน เวียนหัว | ยาแก้คลื่นไส้ |
| ปวดข้อ ปวดกล้ามเนื้อ ปวดหลัง เคล็ด | ยาแก้อักเสบไม่ใช่สเตียรอยด์ |

ศาสตร์ที่อยู่เบื้องหลัง Mock mode คือ Symbolic AI หรือระบบผู้เชี่ยวชาญ ซึ่งเป็นแนวทางเดียวกับที่ MYCIN ใช้เลือกยาปฏิชีวนะเมื่อทศวรรษ 1970 จุดเด่นคือผลลัพธ์คงที่ ตรวจสอบย้อนกลับได้ทุกขั้นตอน และไม่ต้องมีข้อมูลฝึกสอน จุดอ่อนคือไม่ยืดหยุ่นกับภาษาพูดที่หลากหลาย ซึ่งเป็นเหตุผลที่ต้องมี Typhoon มาเสริมในโหมดจริง

### การจัดการคำตอบที่ไม่สมบูรณ์จากโมเดล

ภาษาไทยกินโทเคนมากกว่าภาษาอังกฤษหลายเท่า คำตอบของโมเดลจึงถูกตัดกลางทางได้ถ้าจัดสรร prompt ไม่ดี ระบบจัดการเรื่องนี้ไว้สี่ชั้น

ชั้นแรก schema กำหนดให้เขียนขั้นตอนการทำแผลเป็นฟิลด์แรกเสมอ เพราะเป็นส่วนที่ใช้งานจริงที่สุด ถ้าถูกตัดก็ยังได้ส่วนสำคัญไว้ ชั้นที่สอง prompt สั่งห้ามเขียนคำบรรยายเชิงสรุปใดๆ และจำกัดความยาวรายข้อ เพราะค่าตัวเลขระบบคำนวณและแสดงเองอยู่แล้ว ชั้นที่สาม `_salvage_json()` กู้ JSON ที่ถูกตัดโดยปิดเครื่องหมายคำพูดและวงเล็บที่ค้างอยู่ให้ครบ แล้วตัดรายการสุดท้ายที่เขียนไม่จบทิ้ง ชั้นที่สี่ ถ้ากู้แล้วยังไม่ได้ขั้นตอนที่ใช้งานได้ ระบบถอยไปใช้ขั้นตอนจากกฎมาตรฐานในเครื่องแทน พร้อมแสดงแถบเตือนให้เจ้าหน้าที่รู้ว่าคำแนะนำนี้ไม่ได้มาจากโมเดล

ข้อความสรุปลักษณะแผลคำนวณในเครื่องด้วย `local_assessment()` จากค่าสัดส่วนเนื้อเยื่อ ไม่ผ่านโมเดล จึงได้ผลคงที่ทุกครั้งและไม่มีทางถูกตัด

### การค้นคืนคู่มือแบบออฟไลน์

ออกแบบให้ไม่เรียกเครือข่ายเลยแม้แต่ครั้งเดียว เพราะ รพ.สต. หลายแห่งอินเทอร์เน็ตไม่เสถียร ใช้ BM25 ซึ่งเป็นสูตรจัดอันดับเชิงสถิติที่เขียนไว้ตายตัว ไม่ต้องดาวน์โหลดโมเดล ไม่ต้องใช้ embedding และอธิบายได้ว่าเอกสารถูกเลือกเพราะวลีใดตรงกัน

การทำงานแบ่งสองขั้น ขั้นสร้างดัชนีต้องใช้ตัวอ่าน PDF ทำครั้งเดียวตอนเพิ่มเอกสาร ส่วนขั้นใช้งานจริงอ่านแค่ไฟล์ดัชนี ใช้เฉพาะไลบรารีมาตรฐาน ไม่ต้องมี PDF ต้นฉบับ

การตัดคำภาษาไทยใช้ pythainlp ถ้าเครื่องมี ถ้าไม่มีจะถอยไปใช้ n-gram ระดับตัวอักษรซึ่งเป็นวิธีมาตรฐานสำหรับการค้นคืนภาษาไทยและทนต่อความผิดพลาดของการแตกข้อความจาก PDF ได้ดีกว่า ดัชนีบันทึกไว้ว่าสร้างด้วยตัวตัดคำใด ถ้าตอนค้นใช้คนละตัวระบบจะเตือนให้สร้างใหม่

เอกสารที่ได้ข้อความจาก OCR ถูกกำกับว่าคุณภาพต่ำกว่า และผลค้นจากเอกสารนั้นจะมีข้อความเตือนให้เจ้าหน้าที่เปิดต้นฉบับหน้าที่ระบุเพื่อยืนยัน เพราะ OCR ภาษาไทยอ่านเนื้อความได้ดีแต่เพี้ยนมากกับภาษาอังกฤษและตาราง

ดัชนีปัจจุบันสร้างจากเอกสาร 7 ไฟล์ ได้ข้อความ 1,152 ท่อน คำในดัชนี 17,744 คำ

### PubMed

## ตัวจำแนกประเภทแผลจากคลังภาพ

`wound_classifier_service.py` จำแนกประเภทของแผลโดยเทียบภาพกับคลังภาพที่จำแนกไว้แล้วใน `data/Image_Classifier` ซึ่งมี 10 คลาส ได้แก่ แผลถลอก แผลฟกช้ำ แผลไหม้ แผลบาด แผลเบาหวาน แผลฉีกขาด ผิวหนังปกติ แผลกดทับ แผลผ่าตัด และแผลจากหลอดเลือดดำ

วิธีทำงานคือถอดคุณลักษณะด้วยกฎตายตัวสี่กลุ่ม ได้แก่ HSV histogram, สัดส่วนชนิดเนื้อเยื่อที่ใช้กฎชุดเดียวกับ `wound_service`, ค่าเฉลี่ยและส่วนเบี่ยงเบนของแต่ละ channel และสถิติ gradient ที่ใช้แทนพื้นผิว จากนั้นสุ่มภาพอ้างอิง 5 ภาพจากทุกโฟลเดอร์ เทียบความคล้าย แล้วใช้ค่าเฉลี่ยของ 3 อันดับแรกเป็นคะแนนของโฟลเดอร์นั้น

ต้องระบุให้ตรงเมื่ออธิบายทางวิชาการว่าวิธีนี้ไม่ใช่ rule-based ล้วน การเทียบภาพเข้ากับตัวอย่างที่มี label แล้วเลือกคลาสที่คล้ายที่สุดจัดเป็น instance-based learning หรือ lazy learning ซึ่งอยู่ในตระกูล k-NN เป็น machine learning แบบคลาสสิก ส่วนที่เป็นกฎตายตัวจริงคือขั้นตอนถอดคุณลักษณะ จุดแข็งที่แท้จริงของวิธีนี้คือแสดงได้ว่าเทียบกับภาพอ้างอิงไฟล์ใดบ้างและได้คะแนนเท่าไร ซึ่ง deep learning ทำไม่ได้

ระบบมีตัวกันภาพนอกขอบเขต ถ้าคะแนนดิบอันดับหนึ่งต่ำกว่า 0.30 จะไม่ทายประเภท แต่แจ้งว่าภาพอาจเบลอหรือถ่ายไม่ตรงแผล และถ้าคะแนนอันดับหนึ่งกับอันดับสองห่างกันน้อยกว่า 8 เปอร์เซ็นต์จะแจ้งว่ายังแยกประเภทไม่ชัด ให้เจ้าหน้าที่ระบุเอง

โมดูลนี้และโมดูลค้นคืนคู่มือยังไม่ได้ต่อเข้ากับ API หลัก ใช้งานผ่านเครื่องมือบรรทัดคำสั่งได้แล้ว แต่ยังไม่ปรากฏบนหน้าเว็บ

## ความเป็นส่วนตัวและความยินยอม

ระบบออกแบบให้ไม่เก็บข้อมูลที่ระบุตัวบุคคลตั้งแต่ระดับโครงสร้างฐานข้อมูล ตาราง `session_logs` ไม่มีคอลัมน์สำหรับชื่อ เลขบัตรประชาชน ที่อยู่ หรือเบอร์โทรศัพท์เลย จึงไม่มีที่ให้เก็บแม้จะเผลอส่งเข้ามา

การป้องกันมีสามชั้น ชั้นแรกภาพถูกลบ EXIF และพิกัด GPS ทิ้งทั้งหมดก่อนบันทึก ชั้นที่สอง `scrub_pii()` กรองรูปแบบเลข 13 หลัก เบอร์โทรศัพท์ อีเมล และวันที่ ออกจากบทสนทนาก่อนบันทึก ชั้นที่สาม การบันทึกจะเกิดขึ้นก็ต่อเมื่อได้รับความยินยอมเท่านั้น ถ้าไม่ยินยอมข้อมูลจะไม่ถูกเขียนลงฐานข้อมูลเลย

ข้อความขอความยินยอมเป็นข้อความคงที่ที่เขียนไว้ล่วงหน้า ไม่ได้ให้ AI สร้างใหม่ทุกครั้ง เพื่อให้ถ้อยคำทางกฎหมายคงเส้นคงวา

เปิดเซิร์ฟเวอร์ไว้แล้วรัน `python tests/test_flow.py` ชุดทดสอบครอบคลุมการเข้าสู่ระบบ บัญชียา บทสนทนา Medicine Mode การตรวจจับ red flag ทั้งด้านอาการและบาดแผล การวิเคราะห์ภาพ การกรอง PII และการโหลดหน้าเว็บทุกหน้า รวม 55 รายการ

## ข้อจำกัดที่ต้องรู้ก่อนนำไปใช้จริง

ระบบยังไม่ผ่านการตรวจสอบโดยบุคลากรทางการแพทย์ ห้ามนำไปใช้ตัดสินใจกับผู้ป่วยจริงก่อนผ่านการตรวจสอบ ทั้งกฎความปลอดภัย 15 ข้อและตารางยาทดแทนล้วนยังไม่ผ่านการรับรอง

การวิเคราะห์ภาพใช้การจำแนกค่าสีในปริภูมิ HSV ซึ่งเป็นวิธี rule-based ที่โปร่งใสและอธิบายได้ แต่ยังไม่ใช่ deep learning เส้นทางอัปเกรดคือเปลี่ยน `segment_from_bbox()` ไปเรียก Segment Anything Model ซึ่งรับ prompt แบบกรอบสี่เหลี่ยมได้ตรงกับ UX ที่ออกแบบไว้พอดี แล้วส่ง mask เข้า `analyze_region()` เดิมโดยไม่ต้องแก้ส่วนอื่น

ข้อจำกัดที่ตามมาจากการดูแต่ค่าสีคือระบบแยกไม่ออกระหว่างบาดแผลเปิดกับผื่นแดงบนผิวหนัง ภาพผื่นแดงกระจายจะถูกอ่านว่ามีเนื้อแดงเต็มพื้นที่ ซึ่งเป็นการตีความที่ผิด การต่อ `wound_classifier_service` เข้ามากรองก่อนจะช่วยจุดนี้ได้ เพราะคลาสผิวหนังปกติในคลังภาพจะจับกรณีแบบนี้ได้

การประมาณขนาดแผลเชื่อถือได้ก็ต่อเมื่อเจ้าหน้าที่ระบุขนาดอ้างอิงของภาพ ถ้าไม่ระบุ ระบบจะไม่ใช้ค่าขนาดในการบังคับส่งต่อ แต่แจ้งเป็นข้อสังเกตให้ไปวัดจริงแทน

ฝั่งการจ่ายยายังไม่มีเอกสารอ้างอิงในคลังคู่มือออฟไลน์ ต้องเพิ่มบัญชียาหลักแห่งชาติหรือคู่มือการใช้ยาอย่างสมเหตุผลลงใน `data/Guide_Book/medicine/` ก่อนจึงจะเปิดใช้การค้นคืนหลักฐานฝั่งยาได้

คลังภาพอ้างอิงมาจากชุดข้อมูลที่ถ่ายในบริบทคลินิกซึ่งแสงและพื้นหลังเป็นมาตรฐาน ต่างจากภาพที่ อสม. ถ่ายด้วยมือถือในแสงจริง ต้องทดสอบซ้ำด้วยภาพจากสภาพใช้งานจริงก่อนเชื่อผลลัพธ์

## แผนพัฒนาต่อ

ลำดับความสำคัญที่ควรทำต่อคือต่อ `knowledge_service` และ `wound_classifier_service` เข้ากับ API หลักเพื่อให้ปรากฏบนหน้าเว็บ เพิ่มเอกสารอ้างอิงด้านยาเพื่อเปิดใช้การค้นคืนหลักฐานฝั่งการจ่ายยา แยกสิทธิ์การใช้งานระหว่างเจ้าหน้าที่วิชาชีพกับ อสม. ให้ต่างกันตามขอบเขตหน้าที่ตามกฎหมาย เปลี่ยนระบบยืนยันตัวตนเป็นรหัสหน่วยบริการจริงพร้อม hash รหัสผ่าน และให้บุคลากรทางการแพทย์ตรวจสอบกฎความปลอดภัยกับตารางยาทดแทนทั้งหมด
